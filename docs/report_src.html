StudFinder

Describe a LEGO build in plain English. Get the exact parts. Send the list to BrickLink.

Author Duke Wu
Course AI for Managers, Final Project, October 2026
GitHub repo https://github.com/duke-wu-3/Final-Project (public)
Clone git clone https://github.com/duke-wu-3/Final-Project.git, then follow the README. Put .env in the repo folder or the folder above it.
The app Runs locally with one command (python app.py, see the README). It is not hosted online.
One sentence StudFinder's three AI agents turn a builder's idea, like "a sand green coffee shop with a striped awning", into a priced parts list checked against the real LEGO catalog, then export it as a BrickLink Wanted List the builder can buy from in one step.

1. Motivation

Who has the problem. People who design their own LEGO models, called MOCs ("My Own Creation"). This report focuses on new MOC builders: adults getting back into the hobby, teens, and parents building with their kids. They know what they want to build. They do not know what the parts are called, which part numbers exist, or which colors each part is made in.

How they deal with it today. The main place to buy individual parts is BrickLink, the marketplace the LEGO Group bought in 2019. To buy parts there, you search its catalog one part at a time, using catalog names like "Slope 30 1 x 1 x 2/3" (builders call it a "cheese slope") or "Bracket 1 x 2 - 1 x 2". Then you pick one of more than 200 color names and add each part to a Wanted List. A small storefront needs 14 to 20 different parts, so that is 14 to 20 separate searches, each with its own guesswork.

What it costs them. Time and frustration, plus money when they guess wrong:

  • Time: In my user test, a first-time builder needed 3 minutes 16 seconds to find just 6 parts on BrickLink by hand, even with each part described for her, and rated the experience 1 out of 5 for ease. She said she did not know BrickLink "followed a certain language": there were several kinds of windows, some for trains, and she could not tell which one she needed.
  • Wrong parts: many parts look alike ("1 x 2 x 2" and "1 x 2 x 3" windows; "Type 1" and "Type 2" door frames). Ordering the wrong one means another order and another shipping fee.
  • Dead ends: a part a builder picks may never have been made in the color they want, or may be rare and expensive. BrickLink only shows this after you look the part up.

Two ways people build MOCs. Some builders design digitally first, in 3D software like BrickLink Studio, which already exports a parts list and makes instructions. Many others free-build: they gather a palette of parts in their color scheme and work the model out by hand, with no instructions. StudFinder is for the second group, and for builders who want to start with real parts rather than learn 3D software. What they need is not instructions; it is the right palette of parts: the window that fits, the bracket that lets the sign hang sideways, in colors that exist. StudFinder does not produce building instructions (see Limits).

Why anyone should care. The hard part of a MOC should be the creative part. Today, getting from an idea to a buyable palette of parts is a chore that pushes new builders back to official sets. StudFinder removes that step.

2. What is new here

I looked at what builders use today. Every existing tool assumes you already know the exact parts, or already have a finished digital design:

StudFinder is not trying to be another 3D designer. It covers the step that no tool covers: going from an idea to a buyable palette of parts, for people who build by hand or have not designed anything yet.

Why not just ask ChatGPT? I tested this directly. I gave the same model StudFinder uses (gpt-6-luna) a request for 7 specific parts, with no tools, the way someone would ask a chatbot. I ran it 5 times and checked its part numbers against the real catalog.

The plain model did not make up fake numbers. It gave real numbers for the wrong parts, which is worse: a buyer would trust it and order them. StudFinder's agents never type part numbers from memory. They search the catalog, and every part goes through a check before it can enter the list.

3. The agents

Figure 1. How StudFinder is organized. Python runs the agents in a fixed order: Finder, then Checker; the Refiner runs on each chat message. The agents never talk to each other directly. They share one parts list, and they can only change it through tools that check the real catalog.
AgentWhat it doesTools it can use
FinderSplits the idea into sections (base, walls, windows, roof, details), searches the catalog for each part, and adds parts with realistic quantities. Finishes with a 2 to 3 sentence summary of its assumptions.search_parts, part_colors, add_part
CheckerQuality control before anyone buys. Looks up easier-to-find substitutes for rare parts and suggests swaps; the builder decides. Notes missing essentials, for example a door frame with no door.find_substitutes, suggest_swap, add_note
RefinerHandles chat: "make the walls dark tan", "add 2 lamp posts". Makes exactly the requested change.search_parts, part_colors, add_part, change_color, set_quantity, remove_item, replace_part

Design choices and why

  • A fixed pipeline, not agents handing work to each other. The job is the same every time: find, check, refine. A fixed order keeps cost predictable and makes failures easy to trace. Each agent only gets the tools it needs, so the Checker cannot edit the list and the Finder cannot delete parts.
  • Tools do the facts; the model does the judgment. The model decides what a "striped awning" needs. A database query decides whether part 60593 exists and is made in white. The catalog is about 27,000 parts and 59,000 part-and-color combinations, built from Rebrickable's free downloads. Rarity is how many official LEGO sets have included that part in that color.
  • Model: gpt-6-luna on the course Portkey key, the only allowed model. I use the OpenAI Responses API, because this model only supports tool calls through it, with reasoning effort set to low. That setting halves the cost with no loss in quality (see Tokenomics).
  • A person stays in charge. The Checker suggests swaps but cannot make them. The app produces a file; a person uploads it and decides what to buy.

One real run, step by step

The request: "A small coffee shop storefront for my LEGO town: sand green walls with white trim, big front windows, a door in the middle, a red and white striped awning, and a sign above the door. About 16 studs wide." The numbers below come from a recorded run (docs/eval/sample_trace.json). The screenshots show the same request in the browser.

  1. Describe. The builder types the idea or clicks the example (Figure 2).
  2. Finder searches. In one turn it ran 9 catalog searches at once: "brick 1 x 2", "plate 2 x 16", "window 1 x 2 x 3", "door frame", "glass for window", and others. Batching searches like this saves model calls.
  3. Finder builds the list. It added 18 parts in sections (Base, Walls, Trim, Windows, Door, Awning, Sign, Floor), with quantities sized for a 16-stud facade. For example: 32 sand green 1 x 2 bricks, 4 white 1 x 2 x 3 windows with 4 clear glass panes, and red and white tiles for the awning stripes. Each add_part call was checked against the catalog. In another run, the Finder tried a door frame in reddish brown; the check rejected it because LEGO never made that part in that color, and the Finder picked another (Figure 7, bottom entry).
  4. Checker reviews. It recorded two real problems: "The door frame has only a 1×2 tile listed for glazing, not a door panel, so the storefront door is incomplete", and "The single 2×16 base plate is too narrow to support the listed floor pieces." In the browser run it also flagged a rare door frame (7 sets, last made in 2009) and suggested a near-identical one that appeared in 79 sets (Figure 4).
  5. Time and cost. Finder plus Checker took 14.1 seconds and cost $0.0018.
  6. Refine by chat. "Make the walls dark tan instead of sand green, and add 2 black lamp posts out front." The Refiner recolored all three wall parts in one change_color call, searched for a lamp post, added 2, and replied in one sentence. That took 5.6 seconds and cost $0.0003 (Figure 5).
  7. Export. "Copy for BrickLink" produces BrickLink's XML upload format, with BrickLink's own color numbers, to paste on BrickLink's upload page (Figure 8).

Added after the user test: price estimates

My tester asked to see "the effect an 'uncommon' part might have on the overall cost," so I added BrickLink price estimates the same day. Each part now shows an estimated price and line total, and the list shows an estimated total (Figure 10). The estimate is the quantity-weighted average price that new copies of that part, in that color, sold for on BrickLink over the last 6 months.

A script (scripts/fetch_bricklink_prices.py) reads only the summary at the top of BrickLink's public price-guide page, one request per second. It covered the 968 most common part-and-color combinations plus every combination used in testing, and saved a dated snapshot in the repo, so the app needs no BrickLink login and works offline. The Checker sees prices too: it now also reviews any part over $1 each and says how much a swap saves. The data already caught a real trap: a 1×1 clip plate (61252) sells for about 3 cents in black but about $16 in reddish brown (23 sales in 6 months).

Figure 10. Price estimates: each part's estimated price and line total, and the list total in the header (a storefront list: about $9.60 for 15 of its 17 parts). The asterisk means some parts have no stored price yet, and they are left out of the total.

What it costs per user and at scale

Assumption: an active builder plans 4 builds a month. Each build takes 2 "find" runs (one first try, one redo) and 8 chat edits. That is 4 × (2 × $0.00185 + 8 × $0.0003) = about $0.024 per user per month.

UsersModel cost per monthNotes
1 builder$0.02Less than one LEGO brick.
100 builders (a large LEGO user group)$2.44
10,000 builders$244At medium reasoning the "find" runs alone would cost about twice as much: $0.00386 vs $0.00185 per run.

Not included: hosting. The app runs locally today, and a small cloud server would add roughly a fixed monthly fee. The daily token budget would need to be raised for 10,000 users (see Safety).

What I did to keep cost down

  1. Tools instead of tokens. The catalog search is a database query that costs nothing. The model only reads the top 8 results, with short field names.
  2. Prompt caching. Each agent's instructions and tool list are identical across calls and come first, so OpenAI caches them, and cached tokens cost a tenth as much. In the test runs, 69% of input tokens were cached. Without caching, the same average run would cost about $0.0034 instead of $0.0019, so caching cuts the cost of a run by 46%.
  3. Low reasoning effort (the experiment above): 52% cheaper and 44% faster, with the same essentials coverage (32/33 both ways). The low setting also had no failures. In an earlier test round, before a fix described in Safety, one medium run used up its output allowance thinking and returned no parts at all.
  4. Batching. The Finder runs many searches in one turn, and the Refiner can recolor many parts in one call. Before I added the batch recolor tool, a "make the walls dark tan" request used up its 8-call limit without finishing. After, it took 4 calls and cost $0.0003.
  5. Blocking attacks before the model. An obvious injection attempt costs 0 tokens.
  6. Portkey's response cache. Identical requests are answered from Portkey's cache in under a second with no model call, which happens when people click the same example build. The app reads Portkey's cache-hit flag and counts those calls as $0.

Did cost cutting hurt performance? Not in these tests. Low effort matched medium on essentials coverage and got 7 of 7 on the known-answer test in all 5 runs. Medium produced somewhat longer lists (18.7 vs 14.3 parts), which is more detail but not more correct.

Malfunctions found in testing, and the fixes

1. A silent empty list. In one medium-effort test run, the Finder used up its output allowance thinking and returned no parts and no message. A user would have seen a blank list. Fix: when a reply comes back empty, the agent is told to continue and finish with its tools. If the list is still empty, the user sees a clear "try again" error. I also raised the output allowance per call to 2,500 tokens. After the fix, all 12 runs in the next test round produced lists.

2. A search miss that looked like a wrong answer. Asked for "a white 1x2x3 window frame", the Finder kept choosing a 1x3x3 frame. The cause was the search: the catalog calls the part "Window 1 x 2 x 3 Flat Front", with no word "frame". Fix: when an exact search finds little, it now retries with one descriptive word dropped at a time, keeping the sizes. After the fix, the same request scored 7 of 7 in 5 of 5 independent runs.

3. A cost meter that overcharged. Portkey answers repeated identical requests from its cache, but the API still reports the original token counts, so the app was charging free calls at full price. It also meant early repeat test runs were not independent. Fix: the app reads Portkey's cache-hit flag and records those calls as $0, and every test request is now made unique.

Known limit: the injection filter is a simple pattern match, so a clever attacker can phrase around it. That is why the real protection is inside the tools: no wording can make add_part accept a fake part or a quantity over the cap.

What the numbers mean

Speed: with the same accuracy, she was 6.3 times faster with StudFinder. By hand she averaged about 33 seconds per part, and that was with every part described precisely in the test. A builder starting from a vague idea would not have those descriptions, so real searches would likely take longer. At her pace, a 15-part build like the storefront means about 8 minutes of searching by hand, against well under a minute with StudFinder (about 17 seconds of agent time, then reading the list). The bigger difference is effort: she rated BrickLink 1 out of 5 and StudFinder 5 out of 5.

  • Accuracy, measured by AI-run tests: 7 of 7 parts with both part and color right, in 5 of 5 runs. A plain chatbot averaged 3.6 of 7 on the same request.
  • Speed, measured: a complete list for a 14 to 18-part build in about 17 seconds of agent time on average.
  • Cost: about $0.024 per builder per month, so a LEGO user group or school club with 200 members could run it for about $5 a month.
  • Something that was hard before is now easy: a builder with only an idea, no 3D model and no part names, can get a buyable BrickLink list.

Sources: friend test (n = 1, remote, 26 October 2026); docs/eval/results.json and docs/eval/baseline.json (AI-run tests, 23 October 2026). These are small samples, not a controlled study.

7. Limits and next steps

What doesn't work yet

  • Part numbers: the common ones are fixed, rarer ones are not checked. The catalog uses Rebrickable's numbers. In my own upload test, BrickLink accepted 16 of 18 parts on the first try and rejected two: 3069b and 6141, which BrickLink numbers 3069 and 4073. I then checked the 378 most common parts against BrickLink's catalog: 352 use the same number, 22 use a different one (including the 1×1, 1×2, and 2×2 tiles), and 4 were not found. The export now translates those 22; a few were matched to a closely related mold of the same part. Parts outside that set keep Rebrickable's number, and BrickLink's upload page names any it does not recognize.
  • Prices are a snapshot, not live. They cover the 968 most common part-and-color combinations as of 26 October 2026. Other parts show "no price yet" and are left out of the total. Estimates do not include shipping or store minimums, and prices based on fewer than 10 sales are marked "few sales".
  • No building instructions, and no check that the parts build the model. StudFinder gives a palette of parts, not a design. That suits free-builders, but a builder who wants step-by-step instructions still has to design the model, for example in BrickLink Studio. The Checker catches obvious gaps, such as a door frame with no door, but not every gap. My tester said that for her own idea she would design it in Studio or another app first, then buy, and that StudFinder would be more useful with "a way for me to intuitively create instructions using it." She also asked for BrickLink price estimates, "to see the effect an uncommon part might have on the overall cost." So free-building is not the only use. For builders like her, the next step is the Studio export below.
  • No prices yet. Price checks and choosing stores are left to BrickLink's "Buy All".
  • Small evaluation. One real user. The tasks were always done in the same order (by hand first), so she knew the parts better by Task 2. The by-hand task described each part precisely, which makes BrickLink look easier than it is in real life. The AI tests use 6 builds and 5 repeat runs.
  • The injection filter is shallow (see Safety). The caps and catalog checks are the real protection.

With another month

  1. "Open in Studio": export the list as an LDraw model file, a standard format BrickLink Studio imports, with the parts laid out like a tray. The builder designs with exactly those parts, and Studio produces the instructions and a final parts list.
  2. Suggested build steps, then designs: start with a short, section-by-section build plan from the agents, clearly marked as a rough guide. Fully generated, buildable models are still early research, and today's prototypes only handle simple brick-only models.
  3. Exact BrickLink numbers for every part: the 378 most common are checked; the rest need Rebrickable's API to map them once.
  4. Live prices for any part: today's snapshot covers the 968 most common combinations. BrickLink's official API would price any part on demand, so the Checker could say "swap this rare part and save $8."
  5. "What I already own": import a builder's sets from Rebrickable and subtract those parts before buying.
  6. Photo input: photograph a build you like and get a starting list.
  7. Host it online with logins, and test it with a LEGO user group to get a larger sample.
